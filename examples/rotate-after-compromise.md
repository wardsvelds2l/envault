# Runbook: rotating the master password after a suspected leak

This runbook is for the case where you suspect the master password
for a `envault` vault has been disclosed — to the wrong person, to
a public log, to a third-party service, or to an attacker. It is
written so a single on-call engineer can follow it end-to-end.

If the suspected leak is of a **value** inside the vault (e.g. an
API key that ended up in a blog post) rather than the master
password itself, follow the simpler procedure at the end.

## 0. Confirm it is actually a leak

Before you rotate, make sure the password is in fact compromised.
Common false alarms:

- You saw the password in a CI log, but the log was redacted
  (`***`) — that's a CI masking rule, not a leak. Verify by
  re-running the job and checking that the value printed is
  `***`.
- You saw the password in a teammate's clipboard history, but
  they re-generated it 5 minutes later. Ask them.
- The vault file was attached to a public issue. That is
  **not** a master-password leak — the vault is the encrypted
  artefact. Verify the actual password was not also posted.

## 1. Stop the bleeding (5 minutes)

If the password is still being used live (e.g. it's in a CI
secret that hasn't been rotated), do this **first**:

1. Disable or rotate the CI secret that stores the master
   password. In GitHub: Settings → Secrets and variables →
   Actions → `ENVVAULT_PASSWORD` → Update.
2. In your password manager, mark the entry as compromised so
   you don't accidentally re-paste the old value somewhere.

You now have a window where the vault is committed but cannot be
decrypted by anyone (good!). The next steps restore access with
a new password.

## 2. Pick a new master password (2 minutes)

Generate a new password in your password manager. **Do not** type
it manually. Recommended properties:

- Length: ≥ 20 characters, or a 4–6 word diceware passphrase.
- Randomness: generated by the password manager, not by you.
- Unique: not reused from any other service. The old
  `envault` master password should not appear in your password
  manager under any other entry.
- Stored in: your password manager, under a single entry per
  vault file (e.g. `envault-prod-master`, `envault-staging-master`).

## 3. Re-encrypt the vault locally (5 minutes)

For each affected vault file:

```bash
cd path/to/your/project
export ENVVAULT_PASSWORD=<the new password from step 2>

# Sanity check: the vault still decrypts with the new password
# (it shouldn't — this is to prove the new password is correctly
# set in your shell).
envault inspect            # expected: error, "wrong password"

# Now actually do the rotation. `envault rotate` requires an
# interactive TTY for the new password, so use --password-stdin
# from a password-manager paste, or do it interactively.
envault rotate
# When prompted:
#   - "Old master password": paste the OLD password
#   - "New master password": paste the NEW password
#   - "Confirm": paste the NEW password again
```

`envault rotate` is implemented as a `read → decrypt with old
master key → re-encrypt with new master key → write` cycle. The
on-disk format is unchanged; only the salt and the per-variable
subkeys change.

If you do not have an interactive TTY (e.g. you are in a Docker
container), do it manually:

```bash
# 1. Decrypt to a plaintext .env using the OLD password.
envault unlock --to .env.tmp

# 2. Re-encrypt with the NEW password, writing a fresh vault
# file (it will generate a new salt automatically).
mv .env.vault .env.vault.old
envault lock --from .env.tmp --to .env.vault
ENVVAULT_PASSWORD=$NEW_PW envault get SOME_KEY    # sanity check
rm .env.tmp .env.vault.old
```

## 4. Commit the rotated vault (1 minute)

```bash
git diff .env.vault          # inspect: every per-variable record
                             # should look different (new nonce, new
                             # ciphertext, same KDF algorithm with
                             # new salt)
git add .env.vault
git commit -m "chore(envault): rotate master password after suspected leak

The old master password may have been exposed (see <link to
ticket>). The vault has been re-encrypted with a new password
that is stored in <password-manager-entry-name>.

Refs: <ticket>"
```

The git history still contains the old encrypted vault file in the
previous commit. **This is fine**: the old ciphertext was
encrypted under a different key, and a future reader of the old
commit cannot use it without the old master password. If you want
to be extra cautious, you can rewrite the file from an empty
state and force-push, but this is rarely necessary because the
old master password is no longer in use anywhere.

## 5. Update the CI secret (5 minutes)

For every CI environment that uses the rotated vault:

- GitHub Actions: Settings → Secrets and variables → Actions →
  `ENVVAULT_PASSWORD` → Update.
- GitLab CI: Settings → CI/CD → Variables → `ENVVAULT_PASSWORD` →
  Edit.
- Any other system: wherever the master password is stored, update
  it.

Re-run a job end-to-end to verify the new password is wired
through correctly.

## 6. Notify the team (10 minutes)

- Tell the team what happened, what you rotated, and how to
  re-pull.
- Tell them to delete any local clones of the vault that were
  derived from the old password (in practice: just `git pull`; the
  vault file format is stateless and the local copy will be
  updated by the new commit).
- Tell them to **not** try to use the old password anywhere; it
  is now retired.

## 7. Post-incident (within 7 days)

- [ ] File a retro. The standard questions: how did the password
  leak, what is the new control to prevent the same leak, and
  what is the time-to-detect?
- [ ] If the leak was via a CI log, tighten the masking rules.
  GitHub Actions masks secrets that match the registered
  variable name; if your CI command printed a derived value (e.g.
  `envault get FOO`), that derived value is not automatically
  masked.
- [ ] If the leak was via a shoulder-surf or a screen share,
  remind the team to use `envault --password-stdin` from a
  password-manager paste rather than typing the master password
  in a visible terminal.
- [ ] If the leak was via a stolen developer laptop, rotate
  every other secret that laptop had access to. The vault master
  password is rarely the only sensitive thing on a dev machine.

## Variant: only one value was leaked, not the master password

If you leaked a single API key (e.g. it ended up in a Stack
Overflow question) but the master password is still safe, the
recovery is simpler and you do **not** need to rotate the
master password:

```bash
# In the project:
envault add API_KEY=<the new key value> --comment "Rotated after leak (SO post)"
git add .env.vault
git commit -m "fix(envault): rotate API_KEY after leak"
```

Then revoke the old key at the upstream service that issued it
(Stripe, AWS, etc.). The new key value is encrypted under the
same master password with a fresh nonce; the other variables in
the vault are untouched.
